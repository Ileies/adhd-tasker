# Soon Plan

Status: decided, 2026-10-14. This is the only plan being worked on. It combines the parts of `checks-and-tests-plan.md`, `ux-plan.md` and `feature-ideas.md` that are feasible now and that every later plan builds on. Those parts were removed from their source plans.

## Why one plan first

Every plan in `docs/` changes large parts of the app, so finishing one leaves the others describing code that no longer exists. This plan is finished first. Then it is deleted, the remaining plans are re-read against the new code and updated once, and the next one is picked.

What is in here, and why:

| Part                    | Source                                                     | Why now                                                                                                                       |
| ----------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 1. The gate             | Checks plan phases 0 to 2 (the parts the soon work needs)  | Every later change is verified by one command, and the line numbers in these steps go stale as soon as the UI changes         |
| 2. Pure module tests    | Checks plan phase 3                                        | Cheap, stable, and they guard `rank()` and the time math the hero work builds on                                              |
| 3. Defect fixes         | Checks plan D1 to D8                                       | Real bugs. Part 4 adds new mutations (15 more min, move to later, tomorrow) that need validation, clamping and rollback first |
| 4. Transitions          | UX plan phase 1, hero details from UX section 4, two ideas | The hardest ADHD moment (ending one thing, starting the next) and the biggest UX problems (UX 1 and 2)                        |
| 5. Feedback and silence | UX plan phase 2 and section 12                             | Done has weak feedback and sound can be off without the user knowing (UX 3 and 4)                                             |

What is deliberately not in here:

- **UX phases 3 to 10** (navigation, rail, colors, Plan, task sheet, settings, daylight theme, secondary pages, first run): each one rewrites whole screens. They stay in `ux-plan.md`.
- **Checks phases 4 to 8** (server integration, route matrices, client wiring, e2e, CI): server integration does not go stale because nothing here touches the agent or scheduler code; client wiring tests and e2e specs would be rewritten by the UX phases. They stay in `checks-and-tests-plan.md`.
- **Undecided ideas** from `feature-ideas.md`. Only the two ideas that the decided hero design already covers moved here (Part 4).

Each numbered item is one commit unless noted, small and thematic as `CLAUDE.md` asks. Pure logic first with tests, then components. Every part ends with `bun run verify --quick` (once it exists), and Parts 4 and 5 with a look at the real screen on a wide display and a phone.

## 3. Defect fixes

Each defect was confirmed by running code against the real modules (checks plan section 11). Each gets a failing test first, then the fix, as two commits.

| ID  | Severity | Defect                                                                                                                                                                                                                                                                                                            |
| --- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | high     | `POST /edit` stores invalid tasks. A task at 23:20 (`startTime: 1400`) lasting 120 minutes with `priority: 9` returned 200 and was saved. That breaks "tasks never cross midnight" and the 1 to 5 priority scale `rank()` and `urgencyLevel()` assume. `PUT /edit` has the same gap, and no field is type checked |
| D2  | low      | `POST /edit` without a title answers 500 (`NOT NULL constraint failed: tasks.title`) instead of 400                                                                                                                                                                                                               |
| D3  | low      | `PUT` and `DELETE /edit` answer `200 true` for an unknown or foreign id, and `200 false` for a non-numeric id. Not a leak (queries are scoped), but the client cannot tell success from failure                                                                                                                   |
| D4  | high     | `updateTask` and `deleteTask` in `src/lib/index.ts` change `tasker` optimistically, never check the response and never roll back. Once D1 is fixed, a rejected edit leaves the screen showing a plan the server does not have                                                                                     |
| D5  | medium   | `extend()` in `src/routes/+page.svelte` sets `duration = now - startTime + 15`, which crosses midnight when used after 23:45                                                                                                                                                                                      |
| D6  | medium   | `hooks.server.ts`: with no valid `session` cookie but a `token` cookie, a network error from Google's userinfo endpoint throws, so every request of that user fails with 500                                                                                                                                      |
| D7  | low      | Done (1.0)                                                                                                                                                                                                                                                                                                        |
| D8  | high     | SQLite foreign keys are off (`PRAGMA foreign_keys` is 0 by default in `bun:sqlite`), so every `onDelete: 'cascade'` is inert. Deleting a user, which `/privacy` promises on request, would leave their rows behind                                                                                                |

### 3.1 D8: foreign keys

Turn on `PRAGMA foreign_keys = ON` in `src/lib/server/db/index.ts`. Test: deleting a user removes every row in every table that references it. Before deploying, run `PRAGMA foreign_key_check` on a copy of the production DB, because existing orphans are not reported until they are touched.

### 3.2 D6: `hooks.server.test.ts`

A valid session loads the user; the first login creates the user row; an expired or forged session without a token means no user; the token fallback with a fake userinfo answer logs in; a rejected token clears the cookie; a network error from userinfo means no user and no throw.

### 3.3 D1 to D3: task input and `/edit`

- `parseTaskInput(body, mode)` in a new `src/lib/task-input.ts`, built on the same primitives as `assistant-tools.ts` (`parseTitle`, `parseDuration`, `parsePriority`, the midnight rule), so chat and Plan enforce identical rules. Create requires all fields; update takes a partial patch, and the route checks that the merged task still fits in the day. Status accepts only `pending` and `completed`.
- Route tests in `src/routes/edit/edit.test.ts`: `GET` validates the date and returns only that day; invalid bodies give 400 with the reason, an unknown id 404, a valid create 200 with the row (the status stays 200 so the client contract does not change); every change emits its event with origin `user`.

### 3.4 D5: `extendTask`

`extendTask(task, now, minutes)` in `plan.ts`, clamped to end by 1440. `extend()` on Now uses it. Part 4's "15 more min" is the same helper.

### 3.5 D4: client rollback

`updateTask`, `deleteTask` and `createTask` in `src/lib/index.ts` check the response, restore the previous `tasker` state on failure and show a toast. Tests in `src/lib/index.test.ts` (runes compiled by the preload, fake `fetch`) cover success, a 400 and a network failure for each.

## 4. Transitions

Problems this solves (UX plan review):

1. **A task that runs out silently vanishes from the hero.** `rank()` moves it to `missed` the minute its window ends, the hero switches to the next task or "Free time", and the only trace is a small entry in the rail. A hyperfocused user looks up and sees "Free time" while still on the task. The overrun signal is a toast. There is no "time is up, what now" moment. (`urgencyLevel` even has a level for time below zero, but the hero can never reach it.)
2. **No way to ask for more time on the current task.** "+15 min" only exists for missed tasks in the rail. Running long is the most common case and needs a trip to Plan and a resize.

### 4.1 Hero states

A pure `heroState(ranking, now, settings)` in a new `src/lib/now.ts` (tested) returns one of these states, `NowHero.svelte` only renders it. `rank()` stays as it is, so client and server still agree.

| State           | When                                                                                                                                     | What the hero shows                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **active**      | A task is current, more than the wrap-up threshold left                                                                                  | Time window, title, note, time left, Done, I'm stuck, `...`                                                                    |
| **wrapping up** | Last 10 min or last 25 % of the current task, whichever comes first                                                                      | Same, plus "15 more min" as a ghost button, and the heads-up line for the next task                                            |
| **time up**     | No task is current (or the new current started at the same minute) and the latest unfinished task ended less than its overrun window ago | "Time is up" over the ended task's title, "ended 3 min ago", Done, 15 more min, Move to later. The next task is one line below |
| **free**        | Nothing current, something later today                                                                                                   | "Free time", next task and "starts in"                                                                                         |
| **empty**       | Nothing left today                                                                                                                       | "Nothing left today". The quick add line and "Open Plan" come with UX phase 10                                                 |

The time-up state replaces both the silent switch to "Free time" and the overrun toast, and it is the screen the hyperfocus tap sounds for. When the next task has already started, the hero shows the new task and a slim **transition bar** across its top: "Time for Write intro is up. [Done] [15 more min] [Later]". It stays until answered or until the new task is 15 min old.

**Open, decide at the start of 4.1:** as written, time up ends at the overrun minute, exactly when the hyperfocus tap sounds, so the tap would sound for a screen that just left. Proposal: time up stays until answered, at most twice the overrun window, and the tap sounds at the overrun minute while it is on screen.

The hyperfocus exit ramp idea (`feature-ideas.md`) is this state: "keep going" is 15 more min, "stop" is Done or Move to later. Its "save place and switch" option waits for the "Save your place" idea.

### 4.2 Wrap-up cue

From the wrap-up cue idea (`feature-ideas.md`): entering **wrapping up** plays one soft, distinct `wrap-up` sound (new in `playSound`, display device only, respects mute), unless the heads-up chime for the next task sounds in the same minute. The color shift already happens: `urgencyLevel` rises when under 25 % of the time is left. Once per moment, through `momentKey` like the reminder and overrun sounds.

### 4.3 More time and moving the task

- **15 more min** in wrapping up, time up and the transition bar, through `extendTask` (3.4). Undo toast.
- **`...` menu** on the hero (tier 3): Edit, 15 more min, Move to later today (next free slot), Move to tomorrow, Drop. Every entry has Undo. Edit opens the existing `TaskForm` dialog without leaving Now; UX phase 7 replaces it with the task sheet.
- **`nextFreeSlot(tasks, now, duration)`** in `src/lib/plan.ts` (tested): the first gap after now that fits, on the 15 min grid, never crossing midnight. When nothing fits today, Move to later says so and offers tomorrow.
- The old "+15 min" on missed rail cards uses the same helpers. The rail redesign itself (triage sheet) is UX phase 4.

### 4.4 Heads-up in the hero

"Call dentist starts in 5 min. Start wrapping up." moves from a toast into the hero (wrapping up state, or the free state when nothing is current). The chime stays. A toast could replace an Undo toast and is gone in 8 s, the screen is always on, so a line where the eye goes is better.

### 4.5 Hero details

- **Meta line**: the time window only. The "High priority" label leaves the hero: the urgency color already says it. When several tasks run at once, the meta line says "Highest of 2 right now".
- **I'm stuck** stays secondary, slightly smaller than Done so the hierarchy is clear. Every hint gets one action button: "Start a 2 min timer", "Start a 5 min break" and so on create a short alarm (`POST /schedule`), so the app holds the timer instead of the user. The action lives next to the hint text in `STUCK_REASONS` (`anchoring.ts`, tested).

`CLAUDE.md` (Anchoring) is updated in this part: reminders and the overrun tap are no longer toasts.

## 5. Feedback and silence

Problems this solves:

3. **Completing a task has weak feedback.** Done shows a toast. The only sound is the task-started chime, and only if another task becomes current. Finishing the last task of the block is silent.
4. **Sound can be off without the user knowing.** Browsers block Web Audio until the first tap after a load, so an always-on screen that reloaded overnight plays nothing. Mute has no visible reminder. (The timed mute itself is UX phase 3.)

### 5.1 Done

Done stays the largest control. After a tap the hero shows a short confirmation (check mark, title struck through, about 1.5 s, no motion beyond a crossfade), a distinct warm `done` sound plays (new `playSound('done')`, display device, respects mute), then the hero crossfades to the next state. The toast with Undo stays.

### 5.2 Time

- **Time left in words**: "28 min left, until 15:00" and "1 h 20 min left". The current `0:28` reads like minutes and seconds. New `formatLeft` in `src/lib/format.ts` (tested).
- **Time bar drains instead of fills**: full hero width, thicker (about 12 to 16 px), showing what is left like a Time Timer.
- **Reason line**: only shown after a switch that happened while the page was open, faded out after 60 s. "Scheduled for now" on every load is noise.
- **Tab title** follows the hero: "28 min - Write intro", "Time is up - Write intro", "Free until 15:00". When the app is a background tab instead of a second screen, the tab itself becomes the anchor. Other pages get "Plan - ADHD Tasker" and so on.

### 5.3 Audio unlock and the silence line

- One shared `AudioContext` created on load (today every sound creates its own). Read its `state` and set `tasker.device.audioBlocked` until `resume()` succeeds on the first pointer or key event.
- **Silence line**: "Sound off" when muted, "Tap anywhere to turn sound on" when the browser blocks audio, cleared by the first gesture. At the bottom of the rail on wide screens, in the hero on phones. When UX phase 3 adds the timed mute, the line shows "Sound off until 15:30".

### 5.4 Feedback after this part

| Signal                       | Before                                   | After                                                                             |
| ---------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------- |
| Task done                    | Toast, sound only if another task starts | Hero confirmation, `done` sound, toast with Undo                                  |
| Task ending                  | Nothing                                  | Wrapping up state, `wrap-up` sound, 15 more min                                   |
| Next task soon               | Toast plus chime                         | Hero line plus chime                                                              |
| Overrun                      | Toast plus nudge tone                    | Time-up state or transition bar plus nudge tone                                   |
| Task switch                  | Chime, reason line                       | Same, reason line fades after 60 s                                                |
| Muted                        | Icon in a hidden bar                     | Silence line                                                                      |
| Audio blocked by the browser | Nothing, sounds fail silently            | Silence line "Tap anywhere to turn sound on"                                      |
| Undoable action              | Toast, 8 s, newest replaces older        | Same. Toasts are now only for Undo, so a reminder can no longer push an Undo away |
